# 昆仑 (Kunlun) 模式

一个 DeepSeek Harness 的 Agent 预设。保留梁神（LiangShen）最有价值的设计，去掉它的
短板，并补上它做不到的能力。

**一句话**：昆仑 = 官方 `standard` 预设 + 7 个明确声明的增强，其余逐行对齐。

---

## 它解决什么问题

梁神的好处是**人格纪律**：它把工作方式写成了可检查的规则，而不是许愿。坏处也在这里 ——
它的纪律依赖一条**被截断的系统提示**，而且它**没有任何持久记忆**，也没有**按任务挑选模型**
的能力。

昆仑把"纪律"和"机制"分开：纪律留在提示里，机制做成**运行时模块**，从**事件流外部**观察
会话。提示里的规则会随上下文漂移失效，模块不会。

---

## 七项增强

### A. 五个行为模块（重塑已有工具的使用方式）

| 模块 | 做什么 | 为什么需要 |
|---|---|---|
| `working-context` | 把事件流折叠成一行 `[Working Context: ...]`，只在变化时重发 | 让"当前在哪"占据保证可见的注意力窗口，而不是和几十条日志抢 Top-K |
| `fact-ledger` | `fact_register`：把硬约束钉住 | 八十轮之前说过的部署密钥，不该被忘掉 |
| `guard` | 空输出长推理 / 重复失败的熔断器 | **人格自己的反思保险丝在失控时也已经掉出上下文了**，必须从外部看 |
| `tool-catalog` | 声明线上呈现，保持目录与线上一致 | 目录和实际挂载漂移是静默故障 |
| `tool-activate` | 分页的命名空间，按需加载 | 工具太多会挤占上下文 |

### B. MCP 持久记忆 —— **唯一增加新能力的一项**

九个 `mcp__memory__*` 工具，跨会话的知识图谱。**已端到端实测**：

> 会话 1 被告知部署密钥 `kunlun-deploy-7F3A`、staging `staging.kunlun.internal:8443`。
> **会话 2 —— 全新的、从没被告知的会话**，回答出了这两个值。**3/3 复现。**

### C. 多模型路由 —— **让子代理跑在别的模型上**

`subagent` 工具接受 `provider` / `model` / `reasoning_effort`，并新增
`list_subagent_models`。**已实测**：

```
委派: provider="d1api"             model="glm-5.3"          → 子代理自报 glm-5.3
委派: provider="deepseek-official" model="deepseek-v4-pro"  → 子代理自报 deepseek-v4-pro
父代理: d1api / deepseek-v4.1-flash
```

**注意**：这需要**两处**都配置。预设里的 `modelSelectionSettings: true` 只是让工具**读**
一个 Host 端偏好；**偏好不写，路由就是个空壳**。安装器会自动写（见下面第 6 步）。

## 安装

```bash
node install.mjs
```

然后**重启 DeepSeek Harness Desktop**，在 `设置 → Agent 预设` 选 **昆仑模式**。

重启是必须的，有三件事在会话启动时才发生：

1. 预设本身在会话启动时组装
2. 路由偏好**在会话启动时采样**（改设置不影响已开始的会话）
3. MCP 记忆服务器随 profile 启动

### 选项

```bash
node install.mjs --dry-run        # 只显示会改什么，不写任何东西
node install.mjs --profile <dir>  # 装到指定 profile
```

### 安装器做了什么

| 步 | 动作 |
|---|---|
| 1 | 把组合文件里的占位符（`@@NODE_EXE@@` 等）解析成本机真实路径 |
| 2 | 安装预设包到 profile |
| 3 | 生成预设注册行 |
| 4 | 把包登记进 profile 的 `package.json` |
| 5 | 把 `selectedDefault` 设为 `kunlun` |
| 6 | **写入路由偏好**（漏了这步，路由静默失效） |
| 7 | 安装技能到 `<dshHome>/skills` |

## 实测数据

**工具面**：53 个工具 / 40,655 B（含 9 个 MCP 记忆工具），核心 7/7
（`read` `write` `edit` `glob` `grep` `pwsh` `skill`）。

**响应延迟**（用户反馈"两分钟才开始回答"的根因）：**白泽在 23.4% 的回合里停下来问问题**，
其它预设只有 0.8%。把人格收紧成**可测的前置条件** + 一条 `Momentum` 规则之后：
**1.4%（3/208），降低 94%**。

**启动**：`prompt` 接受 5 / 7 / 10 ms；带 MCP 启动 3,155 / 4,439 / 4,125 ms。

**对比测试**（第二轮，90 个会话，6 场景 × 5 次 × 3 预设，模型 `d1api/deepseek-v4.1-flash`）：

| 场景 | 昆仑 | 梁神 | standard |
|---|---|---|---|
| 克制（不该动手时） | **3/3 · 4.0 次调用 · 11.3s** | 5.3 · 16.1s | 6.0 · 19.7s |
| 陷阱 | 9.0 · 24.3s | 9.7 · 31.6s | 13.0 · 47.4s |
| 长视野 | 18.3 · 84.6s | 15.7 · 82.5s | 16.7 · 78.0s |

**诚实结论**：在**正确性**上昆轮**没有超过**梁神 —— 60 行的 arena3 任务三者都是满分 65/65。
差距在**风格和成本**：更少调用、更少等待、**远少提问**。

## 验证

```bash
node verify-all.ps1
```

9 个校验器。**每个都做过双向验证**：破坏 → 必须 FAIL，恢复 → 必须 PASS。

一个**不会失败**的校验器比没有校验器更糟，因为它会为一个你根本没看的东西盖章。

## 已知边界

- **Windows 优先**。安装器解析本机 Node 路径；其它平台未测。
- **路由需要两处配置**。只改预设是无效的。
- **`workflow-ptc` 被替换成 `workflow`**。前者在本机**从任何位置都解析不到**
  （profile 和 app.asar 都试过），行永远起不来。替代品提供同一个 `workflowEngine` 服务。
- **技能目录是热加载的**，预设和路由偏好**不是**。
